# Corpus-Driven Tuning(用語料訂規則，不要叫使用者再試一次)

使用者原話（2026-10-09）：「**你是不是應該要先訓練好或找好規則與做法，
不是一直叫我回饋**」。

在那之前的模式是：他玩一局 → 回報一種失效 → 我修一種 → 再玩一局。
那是**把人當測試機**，而且每次只覆蓋他剛好做過的那一種輸入。

## 鐵則

**你第二次要說「你再試試看」之前，先問：這個輸入空間我能不能自己產生出來？**

能產生就產生。常見的輸入就那幾種 —— 列出來、全部跑一遍、把偵測率印成表。

## 什麼時候適用

- 門檻、權重、容忍值要調
- 「某些情況會漏」但不知道是哪些情況
- 使用者回報的失效只有一兩個樣本
- 你正打算憑感覺把 0.3 改成 0.25

## 什麼時候不適用

- 輸入分布本身就是未知的（那要錄真實資料，不是產生）
- 正確答案需要人判斷（翻譯品質、美感）
- 一次性的 bug，有明確重現路徑

## 做法

### 1. 把輸入空間列出來，不要只列失效的那個

使用者回報「畫圓會漏」，你要列的不是「圓」，是**所有常見的動作**：
直線、橫線、斜線、圓、半圓、方形、三角、之字、戳刺。
然後加上**不該被偵測到的對照組**（靜止、慢移、微調）——
沒有對照組的話，放寬門檻永遠能讓偵測率變成 100%。

### 2. 維度要交叉，不要只跑一組參數

把會影響結果的環境變數列出來，交叉跑：

```
動作 12 種 × 取樣率 3 種 × 雜訊 2 種 × 尺度 3 種 × 角度 4 種
```

這個專案就是因為只在「手臂伸直」下測過，漏掉「手肘彎著揮」整個區域
（實測偵測率 26%）。

### 3. 產生器要符合領域的物理／解剖約束

一開始我在自由平面上畫形狀，手根本不受肩膀約束 —— 量出來的數字不能用。
改成「肩膀固定、手肘在球面上、手腕在另一顆球面上，用 two-bone IK 解姿勢」
之後才有意義。

**產生器裡的奇異點會偽裝成發現。** 我用 (方位角, 仰角) 參數化球面，起點正好在
極點，方位角維度整個塌掉 → 「橫線」那一列全是 0%。那是產生器的 bug，
不是演算法的缺陷。**看到某一整列或整欄是 0，先懷疑產生器。**

### 4. 固定亂數種子

會飄的測試比沒有測試更糟 —— 同一份程式跑兩次結果不一樣，就沒辦法用它判斷
「我剛才有沒有改壞」。用 mulberry32 之類的，三行寫得完。

### 5. 用單一指標，兩邊都要卡

取自 gesture spotting 的文獻慣例（Lee & Kim 1999）：

```
reliability = 正確偵測 ÷ (動作總數 + 誤報)
```

**只報偵測率可以靠放寬門檻作弊，只報誤報率可以靠關掉功能作弊。**

### 6. 候選規則並排比，不要只驗證你想做的那個

```
判準                  最差偵測率   誤報率
整段直線擬合長             0%        0%
各段取最大                 0%        0%
各段相加                  88%        0%     ← 選這個
```

三者誤報率都是 0%，所以選涵蓋面最好的。**如果只實作了一個，你不會知道它差。**

### 7. 參數用掃的，不要用猜的

```
 K     偵測率A   偵測率B   誤報
 0      83.0%    70.2%    233
 3      88.7%    73.4%    140
 6      97.0%    85.7%      0
10      95.0%    92.5%      0    ← 總偵測率最高
200     90.4%    90.0%      0    ← 等於關掉這個功能
```

**一定要掃到「等於關掉」的那一端。** 那欄告訴你這個功能到底賺了多少 ——
這例子是 +3.6 個百分點。如果賺 0，就該刪掉而不是調參。

### 8. 門檻訂在實測值下面，不要訂在實測值上

量到 89.4% 就訂 85%，不要訂 90%。訂在實測值上等於宣告「任何風吹草動都算回歸」，
而且 **90% 是在吹牛**。

### 9. 跑不到的格子要寫成「已知限制」，附數字與原因

```
橫線 + 手臂伸直 18%：沿鏡頭軸揮，投影幾乎不變，而手臂伸直時正好是
                     深度最不可信的位置，兩種量法同時失效。
戳刺 0%：刻意的 —— 低於「一刀至少掃過一個前臂」。
```

不寫的話下一個人（或下一個你）會把它當成新 bug 再查一次。

### 10. 把語料接成驗收條件

產生器 + 指標寫成 Gherkin 場景，讓「支援哪些輸入」變成可執行的合約，
而不是散在 commit 訊息裡。

## 反模式

| 錯誤 | 正確 |
|---|---|
| 「你再試試看」（第二次） | 先問這個輸入空間能不能自己產生 |
| 只產生使用者回報的那一種輸入 | 列出整個類別，加上不該被偵測到的對照組 |
| 只跑一組環境參數 | 交叉跑取樣率／雜訊／尺度／角度 |
| 某一整列 0% → 宣布發現 | 先懷疑產生器有奇異點或邊界 bug |
| 用 `Math.random()` | 固定種子，不然沒辦法比較前後 |
| 只報偵測率 | reliability，兩邊都卡 |
| 只實作一個候選規則 | 並排比，不然不知道它差 |
| 掃參數但不掃到「等於關掉」 | 掃到底，才知道這功能賺了多少 |
| 門檻訂在實測值上 | 訂在下面留餘裕 |
| 跑不到的格子就不提 | 寫成已知限制，附數字與原因 |
