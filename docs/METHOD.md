# 用一般視訊鏡頭取代 Kinect 的體感切水果：方法與量測

*最後更新 2026-10-09*

---

## 摘要

本文記錄一個純前端體感切水果的做法與量測：以一般視訊鏡頭取代 Kinect 的深度相機，
在瀏覽器裡以 TensorFlow.js + MoveNet 做單人姿態估計，從**肩－肘－腕三點**推出
「掌刀」位置，並判定玩家是否揮出了一刀。

核心的技術難題不是姿態估計本身（那有現成模型），而是三件事：

1. **從不可靠的偵測值裡挑出真手臂** —— 模型對沒舉起的那隻手一樣會吐出一組座標。
2. **在連續動作流裡找出「這是一次揮擊」** —— 文獻稱為 *gesture spotting*。
3. **處理單目的深度歧義** —— 手臂朝向鏡頭時，投影長度會嚴重低估真實動作。

分別用序列機率比檢定（SPRT）、分段掃過長度、以及 Taylor 的逐段 2D→3D 還原處理。
最終在 12 種常見手勢的合成語料上達到
**支援區域偵測率 95.0%、彎手臂 92.5%、誤報 0%**。

---

## 1. 問題

### 1.1 目標與限制

| | |
|---|---|
| 輸入 | 一般網路攝影機，640×480 或 1280×720，無深度資訊 |
| 執行環境 | 瀏覽器，純前端，無後端 |
| 延遲預算 | 推論 ≤ 30ms，畫面 60fps |
| 使用情境 | 一人站或坐在鏡頭前 2–3 公尺，可能只舉一隻手 |

### 1.2 這題為什麼不是「姿態估計」

姿態估計是解決了的問題 —— MoveNet / BlazePose 都能用。真正的難題在它之後：

**模型永遠回傳 17 個關節點，包含它根本看不到的那些。** MoveNet SinglePose 對
「沒舉起的那隻手」一樣會猜一組座標，分數通常 0.1–0.3。那些猜測值在畫面上
常常疊在真手臂附近，於是「一隻手長出兩把刀」。

**單目沒有深度。** 手臂朝向鏡頭揮動時，投影長度可以縮到接近 0 —— 玩家明明揮了
一大刀，程式量到的位移卻幾乎是零。

**連續動作沒有邊界。** 玩家不會按「開始揮擊」再按「結束」。要在一條連續的
軌跡流裡決定「這一段是一次揮擊」，那是 gesture spotting 問題。

## 2. 系統

### 2.1 管線

```
相機影格
  → estimatePoses              MoveNet Lightning，17 點
  → stabilize                  左右修正、跳動閘門、骨長閘門
  → feedCalib                  身形校正（前臂長、雜訊地板、信心水準）
  → updateTracks               SPRT 手臂身分確認
  → armsDistinct / weakerArm   兩條鏈不能共用點
  → bladeFor                   掌刀幾何 + Taylor 逐段深度還原
  → 軌跡 → activeRun → segments → sweepOf
  → slashing 判定 → 命中判定 → 繪製
```

### 2.2 兩條解耦的迴圈

| | 內容 | 排程 |
|---|---|---|
| `renderLoop` | 物理、命中、繪製、面板 | `requestAnimationFrame`，**全同步** |
| `inferLoop` | `estimatePoses` | `setTimeout`，唯一會 `await` 的地方 |

**`requestAnimationFrame` 的回呼必須是同步的。** 原本 `await estimatePoses` 寫在
rAF 回呼裡，瀏覽器要等整個 async 函式走完才畫下一幀 —— 遊戲幀率被綁死在推論速度上，
推論 30ms 就只能 33fps。拆開之後畫面穩定 60fps、推論獨立跑在 30/秒。

**迴圈世代 token**：每次 `startLoops()` 遞增 `loopToken`，舊迴圈發現 token 對不上
就自己退場。光檢查 `running` 不夠 —— 切換模型時舊的 `inferLoop` 可能正卡在 `await`
中間，resolve 時 `running` 已經被重設為 `true`，它就會繼續跑成第二條推論迴圈。

## 3. 方法

### 3.1 模型選擇

| | 輸入解析度 | 大小 | 瀏覽器實測 |
|---|---|---|---|
| **MoveNet Lightning** | 192×192 | 4.5MB | MacBook Pro 104fps、Pixel 5 34fps |
| MoveNet Thunder | 256×256 | 12MB | 慢 2–3 倍 |
| BlazePose | — | — | 53fps / 11–12fps |

選 Lightning。掌刀只需要手腕與手肘這種大關節，不需要 BlazePose 的指節點
（而且那 33 點裡的「手指」是**指節（MCP）**，每指一個，沒有指尖）。

### 3.2 抖動與跳動是兩個問題

| | 成因 | 解法 |
|---|---|---|
| **抖動** jitter | 小幅高頻雜訊 | 濾波 |
| **跳動** jump | 偵測錯誤：點瞬間移到別處 | 離群值剔除 + 身分追蹤 |

**濾波治不了跳動** —— 平滑一個錯誤的點只會得到一個平滑地移到錯誤位置的點。

抖動用 tfjs 內建的 **One Euro Filter**（Casiez et al., CHI 2012）：

```
α = 1/(1 + τ/Te),   τ = 1/(2π·fc),   fc = minCutOff + β·|ẋ|
```

截止頻率隨速度自適應：慢的時候重度平滑（抖動看得見、延遲看不見），
快的時候放寬（不削揮擊尖峰）。**不要在這之上再疊一層 EMA** —— 兩層濾波只會多加延遲。

**傅立葉不適用**：FFT 需要時間窗（延遲）、假設訊號穩態週期，而揮一刀是一次性暫態。
同家族裡能用的是 Savitzky-Golay（視窗內多項式擬合，能保住尖峰），但置中視窗一樣有延遲。
**Kalman 也不適合**：它會把真實快速動作連同雜訊一起衰減。

### 3.3 身形校正：滾動估計 + CUSUM

所有門檻原本都寫成「畫面寬的比例」，那已經比寫死像素好，但**畫面寬跟這個人的手臂
多長沒有關係**。改成持續量測、換算成身體尺度。

三個自適應量共用同一個機制 `Tracked`（滾動估計器 + 帶遲滯的變化偵測），
差別只有波動性：

| 波動性 | 用在 | 行為 |
|---|---|---|
| `static` | 前臂長、雜訊地板 | 收斂後**鎖定**，只在持續偏離時重量 |
| `slow` | 光線／信心水準 | **持續跟**，但換值要有足夠證據 |
| `live` | 每幀都該更新的 | 不做遲滯 |

#### 變化偵測用真的 CUSUM（Page 1954）

```
C⁺ᵢ = max(0, C⁺ᵢ₋₁ + (xᵢ − T) − K)
C⁻ᵢ = max(0, C⁻ᵢ₋₁ − (xᵢ − T) − K)
C 超過 H 就判定「真的變了」
```

以相對偏離 `z = est/value − 1` 為單位，依慣例 `K = band/2`、`H = dwell × band/2`。

原本用的是「連續 N 次超出門檻」的 run-length 規則。換掉的理由是量出來的
（各 60 次模擬，band = 25%）：

| 偏移 | CUSUM 抓到率／平均次數 | run-length |
|---|---|---|
| +60% | 100% / 71 | 100% / 105 |
| +26%（剛好在 band 邊緣） | 100% / 160 | 100% / 289 |
| **+20%（低於 band）** | **100% / 196** | **0%，永遠抓不到** |
| **+15%** | **100% / 362** | **0%** |
| 純雜訊 ±5% | 不誤觸發 | 不誤觸發 |

run-length 在 band 上是一道硬懸崖；CUSUM 累積的是偏離的量，抓得到小於 band 的
持續偏移，只是比較慢。實務上很重要：有人往前站了 20%（完全合理的幅度），
run-length 永遠不會重新校正。

#### 估計量要用高百分位，不是中位數

**透視投影只會讓線段變短、不會變長。** 所以前臂長的觀測分布是「真實長度」往下
拖出一條尾巴，中位數會被每一幀的前縮系統性低估。實測同一組樣本：

| 估計量 | 估計值（真實 200px） | 誤差 |
|---|---|---|
| 中位數 | 124 | −38% |
| **第 80 百分位** | **172** | **−14%** |

#### 估計器的尺規不能是估計器自己

收校正樣本時要有一道**不經過任何估計器**的健全性檢查。這裡用當幀量到的**肩寬**
（成人前臂 ≈ 0.63 肩寬），因為肩寬是直接量到的，學不壞。

這條是用兩次事故換來的：樣本閘門原本寫成 `if (肩寬可用 && 不合理) 跳過`，
肩膀看不到時整道閘門被略過、什麼長度都收。而「單手舉起、另一邊肩膀只有 0.1x」
是常態不是例外 —— 校正前臂因此先後被學成 **40px** 與 **17px**（真實約 200px），
連帶讓骨鏈檢查變成「前臂超過 88px 就擋」，真手臂一律不合格。

→ 現在是「沒有肩寬就**不收樣本**」，而不是「照收」。

### 3.4 手臂身分確認：序列機率比檢定（SPRT）

這是個**資料關聯**問題：真實世界有 1–2 隻手臂，模型每幀吐出 2 條標好左右的鏈，
要決定哪些是真的。

每一幀是一次觀測，累積對數勝算比（Wald 的 SPRT）：

```
Λ ← Λ + log( P(觀測|真手) / P(觀測|幽靈) )
Λ ≥ A → 確認      A = log((1−β)/α) ≈ +4.55
Λ ≤ B → 丟棄      B = log(β/(1−α)) ≈ −2.99        （α = 1%、β = 5%）
```

好處是**門檻由「願意接受的錯誤率」推導出來，不是挑的**，而每一項證據的權重也是
該特徵在兩種假設下出現機率的比值，不是拍腦袋的 1.5。

三項證據：

| 證據 | P(出現\|真手) | P(出現\|幽靈) |
|---|---|---|
| `chain` 骨鏈幾何成立 | 0.95 | 0.30 |
| `cont` 接得上自己上一幀 | 0.92 | 0.15 |
| `strong` 手腕信心明顯高於門檻 | 0.80 | 0.35 |

#### 決策必須鎖存，不是每幀重測

一開始寫成「每幀重新判斷」，結果已確認的手臂壞**一幀**就失去身分
（Λ 4.55 → −1.63）—— 而那正是揮擊時動態模糊會造成的事。
改成鎖存：越過上界才確認、越過下界才撤銷，中間維持現狀。

#### 兩個踩過的坑

**(a) 證據的來源不可以被「證據不足」本身摧毀。**

```js
if (!confirmed[side] && track[side] <= SPRT_B) chainHist[side] = null;   // 錯
```

`cont` 這項證據完全依賴 `chainHist`。Λ 一碰到下界就把歷史清掉 → 沒有歷史 →
`cont` = 0 → 鏈✓續✗強✓ = **−0.385（負的）** → Λ 釘死在下界 → 歷史又被清掉。
**幾何完全正確也永遠爬不出來，只能重載頁面。**
實機取樣 32 筆全部 `續=false(0.00)`、`Λ=-2.99` 一動也不動。

→ 任何「狀態不好就把某個東西清掉」的寫法，先問：**那個東西是不是恢復所需要的憑據？**

**(b) 證據不是條件獨立的。**

幽靈鏈是「用真手的點拼出來的」—— 它既接得上上一幀（續✓），手腕信心也高（強✓）。
把這兩項跟「幾何成立」平行相加，就造出一個死區：

```
鏈✗ 續✓ 強✓ = −2.639 + 1.814 + 0.827 = +0.0014   每幀往上爬萬分之一
```

既到不了上界也到不了下界，15fps 下要 370 秒（6.2 分鐘）才爬出來。
身體往側邊轉超過 60°（上臂/肩寬 > 1.5）就會進去，而那是揮刀的自然動作。

→ 鏈不成立時「續」不帶資訊，不給分。修後鏈✗ 的最大增量 −1.81。

**新增證據項目時，把所有組合的增量列出來檢查**：

```
鏈✓續✓強✓ +3.793    鏈✗續✓強✓ −1.812
鏈✓續✓強✗ +1.788    鏈✗續✓強✗ −3.817
鏈✓續✗強✓ −0.384    鏈✗續✗強✓ −1.812
鏈✓續✗強✗ −2.389    鏈✗續✗強✗ −3.817
```

#### 骨鏈幾何：只檢查上界

```js
if (upper / shoulderW > 1.5) return false;      // 上臂 vs 肩寬
if (fore  / shoulderW > 1.6) return false;      // 前臂 vs 肩寬
```

**只有上界，沒有下界。** 透視投影只會讓線段變短 —— 所以「太長」一定是配錯手臂，
但「太短」可能只是手伸直指向鏡頭，而那正是切水果最常用的動作。

**也不能用「前臂/上臂的比值」** —— 投影會獨立影響兩段：手肘收在身側、前臂橫向
伸出時，上臂縮成 10px 而前臂 70px，比值 7.0，但那是完全正常的姿勢。
上界只對單一線段成立，對比值不成立。

**尺規要用肩寬，不要用學來的校正值。** 校正值學壞了就會變成一道關掉整條管線的閘門
（見 3.3 的 40px / 17px 事故）。肩寬是這一幀直接量到的，不經過任何估計器。

### 3.5 掌刀幾何

```
掌刀 = 手腕 + K × 前臂投影長 × (手腕 − 基準點 的單位向量)
K = 10cm ÷ 25cm 前臂 = 0.4
```

兩個刻意的設計：

1. **位移量用「投影後的前臂長」而不是校正值** —— 手朝鏡頭時真實的 10cm 在畫面上
   本來就該縮短，縮到 0 是對的。
2. **方向在前臂投影夠長時用手肘**（最準）；手伸直指向鏡頭時前臂縮成幾個像素、
   方向全是雜訊，改用肩膀→手腕當基線（同一條已驗證的鏈，基線長得多）。

**誤差放大**：∂掌刀/∂手腕 = 1.4、∂掌刀/∂手肘 = 0.4，兩者獨立時合成
√(1.4²+0.4²) = 1.456。手腕穩但手肘是猜的時候，看起來是「手在跳」，
實際上跳的是手肘 —— 所以手肘的信心門檻要比手腕嚴（×1.15）。

### 3.6 深度還原：Taylor 的逐段 2D→3D lifting

**問題**：手臂朝向鏡頭揮動時，投影位移接近 0，但那是一次完整的揮擊。

**解法**：Taylor (2000) 的逐段還原。弱透視（scaled orthographic）＋ 已知骨長，
每一段骨頭各自解一次：

```
ΔZ = ±√( L² − (Δu² + Δv²)/s² )
```

論文的兩個結論直接用上：

- **解是一整族，由尺度 s 參數化**，而 s 的下界是 `max(投影長 / 真實長)` ——
  那就是「投影只會變短」的正式版。我們有校正值，s 直接拿來用。
- **每段有獨立的 ± 歧義**（n 段 2^(n−1) 種組合）。用**時間連續性**解：
  取跟上一幀同號的那個根。

#### 為什麼一定要「逐段」

第一版把整條手臂當**一顆球**（肩為心、半徑＝臂長）。那只在手臂伸直時成立 ——
手不是在球**面**上，是在球**體**裡，球面只是外邊界。手肘一彎，手腕半徑就變短，
而球面模型會把那個變短硬解成「手往深處去了」，憑空捏造出 0.9 倍臂長的深度。

逐段就沒有這個問題：手肘彎多少由「肘→腕」那一段自己承擔。

#### 雜訊：z 要大過自己的誤差才採信

```
dz/dd = −d/z   ⟹   σ_z = (d/z)·σ_d
```

`z → 0`（投影長接近骨長、手臂落在鏡頭平面內）時誤差發散。不處理的話，
**靜止的手光靠 ±6px 抖動就能生出 233 次假揮擊**，而同樣條件下純 2D 是 0 次。

採信條件 `z² > d·σ·K`。K 用語料掃出來：

| K | 支援區域 reliability | 彎手臂偵測 | 誤報 |
|---|---|---|---|
| 0（無條件採信 z） | 83.0% | 70.2% | **233** |
| 3 | 88.7% | 73.4% | 140 |
| 6 | 97.0% | 85.7% | 0 |
| **10** | 95.0% | **92.5%** | **0** |
| 200（等於完全關掉 3D） | 90.4% | 90.0% | 0 |

選 K = 10：總偵測率最高（93.8%），比「完全關掉 3D」高 **3.6 個百分點** ——
那 3.6 點就是 Taylor 還原實際賺到的東西。

### 3.7 揮擊判定（gesture spotting）

#### 不能用單幀速度

單幀速度很吵 —— 追蹤抖動會把它頂上去，所以門檻放低會把靜止誤判成在揮、
放高又會漏掉真揮擊，怎麼調都是在兩種壞之間選。

#### 也不能用整段的直線擬合長

揮出去和拉回來是**兩段，但屬於同一個動作** —— 這對應手勢研究裡的
**Kendon 相位模型**：preparation（準備）→ stroke（主筆畫）→ retraction（收回），
三相合起來才是一個 gesture unit。

整段直線擬合會讓來回互相抵消（去 160px、回 160px，投影長還是 160px），
也量不到轉折。

#### 做法：方向反轉處切段，各段擬合長**相加**

三種判準用語料量（每格 400 次）：

| 判準 | 最差偵測率 | 誤報率 |
|---|---|---|
| 整段 fit.len | **0%**（三角形 15fps 全漏） | 0% |
| 各段取最大 | **0%**（之字 30fps 掉到 63%） | 0% |
| **各段相加** | **88%** | **0%** |

三者誤報率都是 0%，所以選涵蓋面最好的。

#### 掉一幀不可以砍斷筆畫

這是使用者回報「手畫圓型時會漏揮動」的真因。沒抓到刀的那一幀把 `prev` 清成 null
→ 下一點 `linked` 必然 false → 筆畫從那裡切開。而 `MAX_LINK_MS`（260ms）與距離
上限這兩個「容忍掉點」的常數被整個繞過 —— 它們存在的理由正是這個。

實測同一段揮擊：舊做法 `fit.len` 240px → **90px**（被砍掉 62%）。

#### 「跳太遠」要用速度，不要用絕對距離

原本是 `dist ≤ 畫面寬的 35%`（640 下 224px）—— 一個絕對的畫面比例，而且不隨影格
間隔變。15fps 下一刀只有 3 個點，掉一點就變成單步 242px > 224px → 接不上。

「跳太遠」本來就等於「速度超過人手極限」，而那個量已經有了。兩個門檻合成一個：
`dist ≤ maxSpeed × dt`。

### 3.8 刀痕與命中判定

**全最小平方直線擬合**（垂直距離最小，不是 y 對 x 的回歸；後者遇到垂直刀痕會爆掉）。
一刀揮下去在 150–250ms 內本來就是直的，所以這是在利用領域事實，而且是對
「已經收到的點」做幾何變換，**零延遲**。

命中判定也用同一條線 —— 順便修掉折線的副作用：鋸齒小段會從水果旁邊繞過去，
明明揮過了卻沒切到。

直線度門檻 0.975 是量出來的（各 2000 次模擬）：

| | 直線度 |
|---|---|
| 真實揮擊（總長 ≥ 88px、抖動 6–14px） | 最小 **0.9859** |
| 1/4 圓弧 | 最大 **0.9641** |
| 1/3 圓、半圓 | 0.92 以下 |
| 原地抖動 | 0.42 |

沒過門檻的照原樣畫折線 —— 那表示它真的是一道弧，不該硬拉直。

## 4. 評估

### 4.1 動作語料

靠使用者玩一局、回報一種失效、修一種 —— 那是把人當測試機，而且每次只覆蓋他
剛好做過的那個動作。常見動作就那幾種，直接全部產生出來跑一遍，用數據訂規則。

**12 種動作**：直線上揮／下砍、橫線、斜線、反斜線、1/4 圓、半圓、整圈、方形、
三角形、之字、戳刺。
**3 種對照組**（不該算一刀）：靜止、慢移、微調。

每種動作在以下維度的交叉組合下各跑 300–400 次：

| 維度 | 取值 |
|---|---|
| 推論速率 | 30 / 15 / 8 fps |
| 掉點率 | 0% / 22%（實機量到的刀刃抓到率） |
| 手臂伸展程度 | 0.4 / 0.6 / 0.75 / 1.0 |
| 動作平面偏離鏡頭 | 0° / 30° / 60° / 75° |
| 前臂長（站位） | 76 / 151 / 210 px |

**姿勢是解剖上成立的**：肩膀固定，手肘在以肩為心、半徑 L₁ 的球面上，手腕在以肘
為心、半徑 L₂ 的球面上。手肘位置用 **two-bone 解析 IK** 算出來（餘弦定理）：

```
cos θ = (L₁² + L₂² − r²) / (2 L₁ L₂)        θ = 手肘內角
```

剩下的自由度是手肘繞「肩－腕連線」轉的 swivel angle。

**固定亂數種子**。會飄的測試比沒有測試更糟 —— 同一份程式跑兩次結果不一樣，
就沒辦法用它判斷「我剛才有沒有改壞」。

**不做機器學習**：這是幾何判準，不是分類問題。樣本要的是「涵蓋面」，
訓練資料要的是「代表性分布」—— 前者產生得出來，後者產生不出來。

### 4.2 指標

取自 gesture spotting 的文獻慣例（Lee & Kim 1999）：

```
reliability = 正確偵測 ÷ (動作總數 + 誤報)
```

**只報偵測率可以靠放寬門檻作弊，只報誤報率可以靠關掉功能作弊，reliability 兩邊都卡。**

### 4.3 結果

修正前後（15fps + 22% 掉點，實機條件）：

| 動作 | 修正前 | 現在 |
|---|---|---|
| 直線／橫線／斜線 | 78–81% | **100%** |
| 1/4 圓、半圓 | 79% | **100%** |
| 整圈 | 94% | 99% |
| 三角形 | **0%** | 86% |
| 8fps 全部 | 約 0% | 77–100% |
| 靜止／慢移／微調（誤報） | 0% | **0%** |

深度還原之後：

| | |
|---|---|
| 支援區域（手臂伸展 ≥ 0.75）reliability | **95.0%** |
| 彎手臂（伸展 0.4–0.6） | **92.5%**（原 26.2%） |
| 誤報 | **0** |

#### 實機驗證（同一個瀏覽器分頁，修前 → 修後）

| | 修前 | 修後 |
|---|---|---|
| 軌跡證據 左／右 | −3.0 / −3.0 | 4.6✓ / 4.6✓ |
| 骨鏈 | 不合理 / 不合理 | 成立 / 成立 |
| 校正前臂 | 40 px | 249 px |
| 刀刃抓到率 | 0.0% | 98.4% |
| 擋下跳動 | 3164 | 13 |

### 4.4 已知的硬案例（量過，不是忘了測）

| 情境 | 偵測率 | 為什麼 |
|---|---|---|
| 橫線 + 手臂伸直 | 18% | 沿鏡頭軸揮：手在動但投影幾乎不變，而手臂伸直時正好是 z 最不可信的位置（d≈L，σ_z 發散），**兩種量法同時失效** |
| 反斜線 + 手肘彎 | 78% | 切向與徑向都只剩一部分 |
| 8fps 的圓／方／三角 | 77–79% | 340–400ms 的動作只有 3 個取樣點，形狀根本沒被取樣到 |
| 戳刺（0.5 個前臂 ≈ 6cm） | 0% | **刻意的** —— 低於「一刀至少掃過一個前臂」 |

## 5. 工程上的優化

### 5.1 啟動時間 5324ms → 45ms（快 118 倍）

tfjs 預設從 `tfhub.dev` 抓模型，而那會重導到 Kaggle 拿簽章網址。
`model.json` 加兩個權重分片，每個都要走一次重導鏈：

| | model.json | shard1 | shard2 | 合計 |
|---|---|---|---|---|
| tfhub → Kaggle | 2.24s | 2.41s | 2.73s | **7.4s** |
| localhost | 0.0011s | 0.0022s | 0.0009s | **4ms** |

把模型放本機，開頁時先用 `HEAD` 試本機、抓不到才回去用 CDN。

**另外把啟動改成漸進式**：相機一好就讓畫面動起來，模型在背景載。
載入期間 `nextSpawn = Infinity` 先不丟水果，不然水果會掉下去白白算成漏接。

### 5.1b 上線之後才看得到的那一段：來源要賽跑，而且比的是吞吐量

上面那張表是本機量的。放到 GitHub Pages 之後，使用者回報「載三分鐘還在等」。
量了才知道 Pages 對大二進位檔限速得很兇 —— 同一份 3.8MB 的權重分片：

| 來源 | 總時間 | 吞吐 | TTFB |
|---|---|---|---|
| localhost | 4 ms | — | — |
| jsDelivr（`/gh/` 來源） | **2.96 s** | 1385 KB/s | 0.50 s |
| GitHub Pages | **89.4 s** | 43 KB/s | 1.45 s |

**32 倍**，而且兩邊的檔案 SHA-256 相同 —— 不是內容問題。

比較難的是「**比什麼**」。兩種直覺的做法都會選錯，而且都是量出來才發現：

| 比法 | 為什麼錯 |
|---|---|
| 比誰先回應（TTFB） | Pages 的 TTFB **比較快**（1.45s vs 2.42s），會選到吞吐量慢 32 倍的那個 |
| 拿小檔當樣本 | 用 `model.json`（168KB）比，jsDelivr 因為邊緣還沒熱 TTFB 7.1 秒輸掉（Pages 1.9s）；但同一時間它抓 4MB 只要 2.96 秒。**小檔量到的是冷啟，不是吞吐量** |

所以直接賽那個最大的檔、比誰先抓完，落後 4 倍以上的立刻中止。
差距大的時候輸家只傳幾十 KB（線上實測 **0 KB**）；差距小的時候兩邊都跑完，
那種情況本來就快。

沒有寫死用 CDN，因為本機同源是 4ms —— 寫死的話本機開發反而變成要上網抓。

### 5.1c 進度：函式庫沒給，就自己抓

`pose-detection` 把 `modelUrl` 直接丟給 `tf.loadGraphModel`，
**沒有 `onProgress` 的傳遞路徑**（翻過 CDN 上的 bundle，`grep -c onProgress` 回 0）。

做法是自己用 `fetch` + `ReadableStream` 讀完，內容丟掉 ——
目的只是把瀏覽器的 HTTP 快取塞熱，tfjs 等一下抓同一個網址就不走網路。
這個假設有驗：tfjs 那三個請求 `transferSize = 0`、`decodedBodySize = 4096KB`，
建立 detector 55ms。

而且改成**開頁就開始抓**，讓 4.6MB 的下載跟「讀畫面上那四行說明」重疊。

### 5.2 量化：體積減半，但精度影響未定

模型**本來就已經是 float16 量化過的**（149 個浮點張量全部帶
`quantization: {dtype: 'float16'}`），所以再轉 uint8 只會再少一半，不是 1/4。

官方 `tensorflowjs_converter` 的再量化只支援 `tfjs_layers_model`，而 MoveNet 是
`graph-model`，所以自己寫了一支（算式取自 tfjs-core 的 `decodeWeight()`）：

```
反量化：v = q · scale + min
量化：  scale = (max − min)/255,  q = round((v − min)/scale)
```

| | 體積 | 建立 detector | 推論中位數 |
|---|---|---|---|
| float16（原始） | 4.82 MB | 45ms | 9.4ms |
| uint8 | **2.50 MB（52%）** | 24ms | 8.6ms |

張量層級的量化誤差最大 0.196%（= 1/(2×255)，半個量化階，理論最小值）。
**精度影響還沒有定論** —— 合成圖上量到信心掉一半，但基準模型自己對那張圖的信心
也只有 0.14，等於在比兩團雜訊。

### 5.3 為什麼不壓縮

量過了，不值得：權重是高熵資料，gzip 只壓掉 8%（17.1MB → 15.9MB）。
而且從 localhost 讀本來就只要 4ms。

### 5.4 畫布解析度：量過才決定

畫布內部尺寸原本 = 相機解析度。視訊被放大是沒辦法的事（相機就那個解析度），
但**我們自己畫上去的東西**不該跟著糊 —— 實測桌機上 640 的畫布被顯示成
1896×1422 裝置像素，**放大 2.96 倍**，文字、刀痕、炸彈的虛線圈全是糊的。

遊戲引擎（Phaser 的 Scale Manager）的做法是把 backing store 設成
「顯示尺寸 × devicePixelRatio」。代價是填充率。做成開關實測：

| | 1× | ×2.96 |
|---|---|---|
| 畫面更新 | 61 /秒 | **60 /秒** |
| 推論耗時中位數 | 10.3 ms | 11.7 ms |
| 像素量 | 307k | 2.69M（**8.76 倍**） |

在 M4 上幾乎免費。但**手機沒量過**，所以：

- 上限訂 **2×**（4 倍像素量，拿到大部分的清晰度）
- 加一道看門狗：開著高解析而幀率連續 3 秒低於 45 就自動退回 1×

與其猜一個「哪些裝置可以」的名單（那是 UA 嗅探，會過時），不如讓它自己量。

座標系的處理：關節點是在相機解析度下的座標，畫布放大之後要跟著乘 ——
**乘在 `inferLoop` 收到關節點的那一個地方**，下游完全不用知道。
那是關節點進入系統的唯一入口。

### 5.5 影格：`requestVideoFrameCallback`

取代輪詢 `video.currentTime`。它在真的有新影格時才觸發，而且 `presentedFrames`
可以算出**漏掉幾格相機影格**。瀏覽器不支援時自動退回輪詢。

**踩過的坑**：rVFC 的續接條件一度寫成 `if (running || phase !== 'idle')`，
但註冊是在 `startCamera()` 裡做的 —— 那時兩個都是 false。於是第一次回呼就不續接，
**整條鏈當場死掉，推論從此不再跑**，而畫面照樣 60fps、面板數字照樣更新。
現在續接只看 `video.srcObject`，另外加一道看門狗：超過 500ms 沒動靜就退回輪詢。

## 6. 已知限制

1. **沿鏡頭軸的揮擊**（見 4.4）—— 單目的本質限制，兩種量法同時失效的唯一區域。
2. **8fps 以下** —— 340ms 的動作只剩 3 個取樣點，形狀沒被取樣到。
3. **雙人以上** —— 用的是 SinglePose 模型。
4. **`z` 的 ± 歧義靠時間連續性解** —— 動作中途真的穿越鏡頭平面時會挑錯號，
   目前靠採信門檻把那些幀的 z 設成 0 來迴避。
5. **16:9 相機** —— 垂直方向的物理常數以畫面**寬**為尺度，16:9 下水果會飛出
   畫面上方最多 1.08 秒。

## 7. 方法論：這個專案犯過的錯

這一節比上面任何一節都重要。

### 7.1 使用者回報執行期異常時，第一個動作是取得數字，不是打開檔案

使用者連續三次回報「手掌沒出現」。我讀程式碼猜了四輪 —— 信心門檻、骨鏈幾何、
左右配對、校正值 —— 四個都合理，四個都錯。真因要讀到跑起來的數字才看得見。

而且是**三個獨立的 bug 疊在一起**，每一個單獨都足以讓功能完全失效。
所以前兩次修完「還是沒有」，看起來像沒修對，其實是還有兩層。

→ **「還是沒有」要當成「還有下一層」，不是「上次修錯了」。**
先用數字確認上一關現在過了，再往下一關找。

### 7.2 診斷要印到 console，不要畫在畫面上

畫面有邊界、有版面、會被裁切。實際發生過：診斷畫在 canvas 的 `y = 0.90 × 高`，
最關鍵那一行超出下緣被切掉，白白多一輪。而且使用者沒辦法複製貼上。

### 7.3 一個恆定不變的數字就是答案所在

```
Λ=-2.99  Λ=-2.99  Λ=-2.99  ...  32 筆取樣一動也不動
續=false(0.00)  續=false(0.00)  ...  全部剛好 0.00
```

「剛好 0.00、一次都沒變」不是巧合，是某條路徑每次都走同一個 early return。

### 7.4 沒跑過變異的測試不算數

把修正還原回去，確認測試真的變紅，再改回來。否則它可能從頭到尾都是綠的。
這個專案的每一條回歸測試都跑過變異。

### 7.5 審查員會誤報 —— 每一項都要親自覆核

兩個獨立審查員都說「校正後揮擊門檻變 2.7 倍嚴」。**不成立** —— 他們拿「校正後
210px」比「調校值 77px」，但那 77px 是在不同身體尺度下量的。使用者坐得近、
前臂在畫面上 151–249px，揮擊掃過的像素也等比變多。

**誤報也要寫下來** —— 不寫的話下一輪會再查一次同樣的東西，而且可能被說服去改
一個其實是對的設計。

### 7.6 同一件事只能判一次

「這是不是兩隻不同的手」原本由 `armsDistinct`（看原始關節點）和刀刃距離
（看算出來的點）各判一次，兩套門檻、兩份資料 —— 一定會漂走。
實機一局量到後者觸發 2164 次，每次讓那隻手整段筆畫作廢。

單一來源靠紀律守不住，要變成**機械檢查**（`tests/singlesource.test.js`）。
