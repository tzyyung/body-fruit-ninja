# 體感切水果 MVP — 可行性與效能量測

用一般視訊鏡頭取代 Kinect。目的是量數字，不是做完整遊戲。

> **方法與理論的完整說明在 [`../docs/METHOD.md`](../docs/METHOD.md)** ——
> 那份寫「為什麼這樣做」（SPRT、CUSUM、One Euro、Taylor lifting、
> gesture spotting、評估方法與結果），這份寫「這裡有什麼、怎麼跑、量到多少」。

## 怎麼跑

```sh
./menu.sh            # 互動選單
./menu.sh open       # 直接開（需要時自動啟動伺服器）
./menu.sh models     # 把模型抓到本機（第一次建議先做）
./menu.sh check      # 自我檢查：語法、CDN、本機模型
./menu.sh status     # 現在有沒有在跑
./menu.sh stop
PORT=9000 ./menu.sh  # 換埠
```

`run.sh` 仍然可用，就是單純起一個伺服器。

**一定要從 localhost 開，不能直接雙擊 HTML 檔。** `getUserMedia` 只在
secure context 下存在，用 `file://` 開的話 `navigator.mediaDevices` 整個是
`undefined` —— 不是權限被拒，是 API 不見了。

## 模型放本機（開頁從 5 秒變 45 毫秒）

tfjs 預設從 `tfhub.dev` 抓模型，而那會重導到 Kaggle 拿簽章網址。
`model.json` 加上兩個權重分片，每個都要走一次重導鏈：

| | model.json | shard1 | shard2 | 合計 |
|---|---|---|---|---|
| tfhub → Kaggle | 2.24s | 2.41s | 2.73s | **7.4s** |
| localhost | 0.0011s | 0.0022s | 0.0009s | **4ms** |

瀏覽器內實測建立 detector 的時間：**CDN 5324ms vs 本機 45ms，快 118 倍。**

`./menu.sh models` 會把兩個 MoveNet 抓下來（Lightning 4.7M、Thunder 12M）。
頁面會先用 `HEAD` 試本機，抓不到才回去用 CDN —— 所以沒跑過這個指令也不會壞。
面板的「模型來源」會顯示現在用的是哪一邊。

用不到 Thunder 的話 `rm -rf models/movenet-thunder` 就好。

### 量化（uint8）

模型**本來就已經是 float16 量化過的**（`model.json` 裡 149 個浮點張量
全部帶 `quantization: {dtype: 'float16'}`），所以再轉 uint8 只會再少一半，
不是 1/4。

```sh
./menu.sh quantize       # 產生 models/movenet-lightning-uint8
```

`quantize.py` 自己寫的，因為官方 `tensorflowjs_converter` 的再量化只支援
`tfjs_layers_model`，而 MoveNet 是 `graph-model`；而且它會拉進
TensorFlow + JAX 幾 GB 的相依。算式取自 tfjs-core 的 `decodeWeight()`：

```
反量化：v = q * scale + min
量化：  scale = (max - min) / 255,  q = round((v - min) / scale)
metadata: {dtype:'uint8', original_dtype:'float32', scale, min}
```

結果：

| | 體積 | 建立 detector | 推論中位數 |
|---|---|---|---|
| float16（原始） | 4.82 MB | 45ms | 9.4ms |
| uint8 | **2.50 MB（52%）** | 24ms | 8.6ms |

張量層級的量化誤差最大 0.196%（= 1/(2×255)，半個量化階，理論最小值）。

**但精度影響還沒有定論。** 用合成假人量到 uint8 的信心只剩基準的一半
（0.143 → 0.067），那是真的退化訊號；可是基準模型自己對那張圖的信心也只有
0.14，等於在比兩團雜訊，位移數字不可信。

要真的答案就按頁面上的**「比對 fp16 / uint8」**：它會用你的即時影像同時跑兩個
模型五秒，輸出手臂關節點的位移中位數／p95 和信心差。真人影像才算數。

### 為什麼不壓縮

量過了，不值得：

| | 原始 | gzip | 比率 |
|---|---|---|---|
| 權重 `.bin` | 17.1 MB | 15.9 MB | **92%** |
| `model.json` | 168 KB | 7.4 KB | 4% |

權重是 float32 高熵資料，gzip 只壓掉 8%。而且從 localhost 讀本來就只要 4ms，
沒有東西可省。真要縮小體積該做的是**量化**（uint8 權重，體積變 1/4），
但那要 `tensorflowjs_converter` 重轉、也會損失精度 —— 等要放上網路或給手機用再說。

## Lightning 和 Thunder 差在哪

同一個模型 MoveNet 的兩個版本，偵測同樣 17 個關節點：

| | 輸入解析度 | 大小 | |
|---|---|---|---|
| Lightning | 192×192 | 4.5MB | 快，預設 |
| Thunder | 256×256 | 12MB | 準，推論慢 2–3 倍 |

掌刀只用到手腕和手肘這種大關節，Lightning 綽綽有餘。

## 開始的順序：相機先亮，模型在背景載

以前是 `await startCamera()` → `await buildDetector()` → 才移除提示框，
所以相機早就好了，畫面卻被壓在模型載入後面，使用者盯著提示框等好幾秒。

現在相機一好就 `startLoops()` 讓畫面動起來，模型在背景載。
載入期間 `nextSpawn = Infinity` 先不丟水果 —— 不然水果會掉下去白白算成漏接。

## 掌刀是怎麼算的

手肘和手腕兩點定出前臂方向，從手腕沿這條線再往前 10cm：

```
掌刀 = 手腕 + 0.4 × (手腕 − 手肘)
```

`0.4` 是 10cm ÷ 25cm（成人前臂長）。用「前臂長的比例」而不是寫死像素，
所以人站遠站近時 10cm 會自動跟著縮放 —— 前臂在畫面上變短，掌刀的偏移量
也跟著變短。面板的「前臂長度」就是在確認這個尺度換算合理（站 2–3 公尺、
640 寬的畫面下大約 60–110px）。

這個算法只需要**手腕**和**手肘**，兩個模型都有，所以可以用最快的
MoveNet Lightning，不必為了手指點去背 BlazePose 2–3 倍的推論成本。

## 預設值與理由

| 項目 | 預設 | 理由 |
|---|---|---|
| 模型 | MoveNet Lightning | 瀏覽器實測比 BlazePose 快 2–3 倍，而掌刀算法不需要它的指節點 |
| 刀刃 | 掌刀（往前 10cm） | 見上 |
| 運算 | WebGL | WebGPU 在 Apple Silicon 上沒有可靠的公開實測，所以不預設，留著自己比 |
| 信心門檻 | 自動 | 跟著「正在用的那隻手」的信心分布走，不是兩隻手混在一起 |
| 要揮出一刀才算 | **開** | 不開的話，一隻靜止的手就是一把半徑 41.6px 的常駐刀，水果飛進去就被切 |
| 抖動平滑 | **開** | tfjs 的 `enableSmoothing` 用的是 One Euro Filter，截止頻率隨速度自適應，**不會**削掉快揮的尖峰 |
| 拉直刀痕 | 開 | 見下 |

## 「有沒有揮出一刀」怎麼判

**不是用單幀速度。** 單幀速度很吵——追蹤抖動會把它頂上去，所以門檻放低會把
靜止誤判成在揮、放高又會漏掉真揮擊，怎麼調都是在兩種壞之間選。

改用**整段軌跡掃過的長度**（直線擬合的 `fit.len`）。那是 280ms 視窗的累積量，
抖動在裡面會互相抵消。等價於一個「280ms 平均速度」門檻，但穩定得多。

門檻 `F.slashMin = 0.12`（畫面寬的 12%，640 寬時約 77px）是量出來的
（各 4000 次模擬）：

| 門檻 | 靜止誤判成揮 | 慢移 200px/s 誤判成揮 | 輕揮 350px/s 被漏掉 |
|---|---|---|---|
| 0.09 | 0% | **32%** | 0% |
| **0.12** | **0%** | **0%** | **0%** |
| 0.15 | 0% | 0% | **31%** |

另外實測 1000px/s 的揮擊在 30fps 與 60fps 下筆畫長度都是 ~280px ——
證實這個判準跟 fps 無關，不像舊的單幀門檻。

## 水果可以重複切

每一塊果肉都帶著「自己被切過哪幾刀」的清單（本體座標系的角度 + 保留哪一側）。
再切一刀就是把那塊複製成兩塊、各自多一個切面。繪製時連續呼叫 `clip()`
會取交集，所以切兩刀自然得到四分之一、三刀得到八分之一 ——
不用為「兩半」寫死一組特例。

- 上限 `MAX_GEN = 3`（八分之一）。到上限的碎塊**切不動**，而不是切了就消失。
- 命中半徑每切一刀縮 `GEN_SHRINK = 0.72` 倍。
- 剛切出來的碎塊有 `PIECE_IMMUNE_MS = 200` 的無敵時間 ——
  否則同一刀的同一條線段下一幀還在，會把它一路切到最細，
  玩家只會感覺到「碰一下就碎光了」。

## 自適應量的共同基礎（Tracked）

會變的、不會變的、緩慢變的，用同一套機制處理：
**滾動估計器 ＋ 帶遲滯的變化偵測**。差別只有「波動性」一個參數。

| 波動性 | 用在 | 行為 |
|---|---|---|
| `static` | 前臂長、雜訊地板 | 收斂後**鎖定**，只在持續偏離時重量 |
| `slow` | 光線／信心水準 | **持續跟**，但換值要有足夠證據 |
| `live` | 每幀都該更新的 | 不做遲滯 |

### 變化偵測用的是真的 CUSUM

```
C⁺ᵢ = max(0, C⁺ᵢ₋₁ + (xᵢ − T) − K)
C⁻ᵢ = max(0, C⁻ᵢ₋₁ − (xᵢ − T) − K)
C 超過 H 就判定「真的變了」
```

以相對偏離 `z = est/value − 1` 為單位，依慣例 `K = band/2`，
`H = dwell × band/2`（剛好 band 大小的持續偏移在 dwell 次後觸發）。

**原本用的是「連續 N 次超出門檻」的 run-length 規則。** 換掉的理由是量出來的
（各 60 次模擬，band = 25%）：

| 偏移 | CUSUM 抓到率／平均次數 | run-length |
|---|---|---|
| +60% | 100% / 71 | 100% / 105 |
| +26%（剛好在 band 邊緣） | 100% / 160 | 100% / 289 |
| **+20%（低於 band）** | **100% / 196** | **0%，永遠抓不到** |
| **+15%** | **100% / 362** | **0%** |
| 純雜訊 ±5% | 不誤觸發 | 不誤觸發 |

run-length 在 band 是一道硬懸崖，低於門檻就永遠偵測不到；CUSUM 累積的是
偏離的量，所以抓得到小於 band 的持續偏移，只是比較慢。對我們很實際：
有人往前站了 20%（完全合理的幅度），run-length 永遠不會重新校正。

（附帶一提：教科書上常說 CUSUM 的好處是「雜訊不會讓計數歸零」。
那個優勢在這條管線裡**不成立**，因為上游的 150 樣本滾動中位數已經把
逐樣本雜訊磨掉了 —— 實測兩者在帶雜訊的大偏移上都是 100% 抓到。
真正的好處是上表那個：對 band 以下的偏移仍然有效，以及偏移越大觸發越快。）

## 自動校正（連續、會鎖定）

所有門檻原本都是「畫面寬的比例」，那已經比寫死像素好，但**畫面寬跟這個人的
手臂有多長沒有關係**。現在相機一開就持續量，數值從預設值逐步收斂到量到的，
使用者完全不用配合做什麼。

| 量到的 | 換算成 |
|---|---|
| 前臂像素長（手肘→手腕的**第 80 百分位**） | 揮擊門檻 = 1 個前臂長；關節極速 = 28 個前臂長／秒 |
| 雜訊地板（每幀位移的第 10 百分位） | 揮擊門檻至少要是它的 6 倍 |
| 關節信心中位數 | 光線差時自動放寬 `MIN_SCORE` |

**雜訊地板不需要請人站著別動**：取最近視窗內每幀位移的第 10 百分位，
任何一段時間裡都有手比較靜的時刻，那些低位移就是雜訊。

**前臂長用第 80 百分位不用中位數**：透視投影只會讓線段變短，所以觀測分布是
「真實長度」往下拖一條尾巴，中位數會被每一幀的前縮系統性低估
（實測同一組樣本：中位數低估 38%、第 80 百分位低估 14%）。

**收樣本前要過一道「不經過估計器」的閘門**：用當幀量到的肩寬
（成人前臂 ≈ 0.63 肩寬）。沒有肩寬就不收，不是照收 ——
這條是用兩次「校正前臂被學成 40px / 17px」的事故換來的。

**收斂後會鎖定（約 1 秒、30 幀）**，之後不再更新。不鎖的話有一個會自己惡化的
迴路：玩的時候手一直在動，連最安靜的時刻都比真正靜止時大 → 雜訊地板緩慢上爬
→ 揮擊門檻升高 → 越玩越難切中，而且查不出原因。門檻在玩的過程中偷偷改變，
本身也讓手感變得不可預測。

鎖定後只做一件事：監看前臂長有沒有偏離超過 25% 且持續 45 幀 ——
那表示人真的走近或走遠了，才解鎖重新量。重玩不會重設校正（那是身形，不會變）。

## 連擊與爆擊

| | |
|---|---|
| 連擊 | 1.1 秒內連續切中，倍率累加，上限 ×5。失手或漏接就歸零 |
| 爆擊 | 8% 機率額外 +10，專屬音效與金色數字 |
| 引信聲 | 炸彈飛行中持續嘶嘶聲，由小漸大。切到或落地就停 |

連擊音高隨連擊數上升，耳朵自己會知道在累積。3 連擊以上畫面上方才顯示，
平常不佔版面。

## 影格與暖機

> **踩過的坑**：rVFC 的續接條件一度寫成 `if (running || phase !== 'idle')`，
> 但註冊是在 `startCamera()` 裡做的 —— 那時候 `running` 還是 false、
> `phase` 還是 `'idle'`（要等模型載完才進 ready）。於是第一次回呼就不續接，
> **整條鏈當場死掉，推論從此不再跑**，畫面上的關節分數全是一張老影格。
>
> 這個失敗模式特別惡劣：畫面照樣 60fps 在動、面板數字照樣在更新，
> 從外面完全看不出推論已經停了。我因此連續猜錯四個方向（門檻、平滑、
> 本機模型、取景），全都是在調停擺的推論結果。
> 最後是面板的「推論更新」顯示 1/秒才抓到。
>
> 兩個修正：續接條件改成只看 `video.srcObject`（串流還在就續接）；
> 另外加一道保險 —— rVFC 超過 500ms 沒動靜就不再信它、退回輪詢。

- **`requestVideoFrameCallback`** 取代輪詢 `video.currentTime`。它在真的有新影格時
  才觸發，而且 `presentedFrames` 可以算出**漏掉幾格相機影格**（面板有這一欄）。
  瀏覽器不支援時自動退回輪詢。
- **模型暖機**：第一次推論要編譯 shader 會卡一下。模型是背景載入的，
  正好在那時候先跑一次空推論，把停頓挪到玩家還沒開始之前。面板顯示它花了多久。
- **「縮圖再推論」開關**：MoveNet 內部會縮到 192×192，但 640×480 的材質上傳成本
  還在。先縮到 256 寬再送「可能」比較快 —— 但 `drawImage` 本身也要錢，
  所以做成開關去量，不要憑感覺決定。

## 關節跳動怎麼處理

**抖動和跳動是兩回事，解法也不同。**

| | 成因 | 解法 |
|---|---|---|
| 抖動 jitter | 小幅高頻雜訊 | 濾波（One Euro，見下一節） |
| 跳動 jump | 偵測錯誤：點瞬間移到別的地方 | 離群值剔除 + 身分追蹤 |

濾波器治不了跳動，因為那不是雜訊，是**錯誤的偵測值** ——
平滑一個錯誤的點只會得到一個平滑地移到錯誤位置的點。

**傅立葉不適用**：FFT 需要時間窗（延遲）、假設訊號穩態週期，
而揮一刀是一次性暫態。同家族裡能用的是 Savitzky-Golay（視窗內多項式擬合，
能保住尖峰），但置中視窗一樣有延遲。
**Kalman 也不適合**：它會把真實快速動作連同雜訊一起衰減，對切水果是致命的。

做了四道，按鈕是「關節穩定化」，可以關掉比較：

1. **整條手臂都要可信**（單手時最有感）。只看手腕的話，垂下或出框的那隻手
   仍會被模型猜出一個位置、偶爾越過門檻，就生出一把到處游移的幽靈刀。
   現在肩、肘、腕三點都要過門檻才算數。
2. **手肘門檻比手腕嚴 1.35 倍**。掌刀 = 手腕 + 0.4 ×（手腕 − 手肘），
   手肘誤差會被放大 0.4 倍帶進來 —— 手腕穩但手肘是猜的時候，
   看起來是「手在跳」，實際上跳的是手肘。
3. **跳動閘門**：單幀速度超過人類極限就丟棄這次偵測、沿用上一個。
   人的手腕全力揮動約 3–4 m/s，站 2.5 公尺時約 1300 px/秒；
   左右互換造成的瞬移在 30fps 下是 6000 px/秒以上 —— 差四倍以上，很好分。
   **實測 1300 px/秒 的全力揮動一幀都沒被擋。**
   連續擋超過 250ms 就放行，因為人可能真的移動了。
4. **左右身分用運動連續性帶過去**：每幀試兩種指派，選跟上一幀最吻合的。
   （單手時這條用不到，但雙手交叉時會。）

面板的「擋下跳動／骨長異常／修正左右／手臂不可信」四個數字會告訴你
各道各擋了多少。

## 刀痕為什麼要拉直

掌刀 = 手腕 + 0.4 × (手腕 − 手肘)，所以手腕的估測誤差在這裡被放大 1.4 倍、
手肘再貢獻 0.4 倍 —— 掌刀點比手腕本身更抖，直接連線就是折線。

分兩層處理，因為是兩個不同的問題：

**點的抖動** → tfjs 內建的 `enableSmoothing`，用的是
[One Euro Filter](https://direction.bordeaux.inria.fr/~roussel/publications/2012-CHI-one-euro-filter.pdf)
（Casiez et al., CHI 2012），也是 MediaPipe 內部用的那一個：

```
α = 1/(1 + τ/Te),  τ = 1/(2π·fc),  fc = minCutOff + beta·|ẋ|
```

bundle 內的預設是 `{frequency:30, minCutOff:0.05, beta:80, derivateCutOff:1}`。
慢的時候重度平滑（抖動看得見、延遲看不見），快的時候放寬（不削揮擊尖峰）。
**不要在這之上再自己疊一層 EMA** —— 兩層濾波只會多加延遲。

**刀痕的形狀** → 全最小平方直線擬合（垂直距離最小，不是 y 對 x 的回歸；
後者遇到垂直刀痕會爆掉）。一刀揮下去在 150–250ms 內本來就是直的，所以
這是在利用領域事實，而且是對「已經收到的點」做幾何變換，**零延遲**。
命中判定也用同一條線 —— 順便修掉折線的副作用：鋸齒小段會從水果旁邊繞過去，
明明揮過了卻沒切到。

直線度門檻 `0.975` 是量出來的（各 2000 次模擬）：

| | 直線度 |
|---|---|
| 真實揮擊（總長 ≥ 88px、抖動 6–14px） | 最小 **0.9859** |
| 1/4 圓弧 | 最大 **0.9641** |
| 1/3 圓、半圓 | 0.92 以下 |
| 原地抖動（不是揮擊） | 0.42 |

沒過門檻的就照原樣畫折線 —— 那表示它真的是一道弧，不該硬拉直。

## 推論與繪製是分開的兩個迴圈

`requestAnimationFrame` 的回呼**必須是同步的**。原本 `await estimatePoses`
就寫在 rAF 回呼裡，瀏覽器要等整個 async 函式走完才能畫下一幀 ——
遊戲幀率被綁死在推論速度上，推論 30ms 就只能 33fps。

現在拆成兩條：

| | 內容 | 排程 |
|---|---|---|
| `renderLoop` | 軌跡過期、筆畫擬合、生成、物理、命中、繪製、面板 | `requestAnimationFrame`，**全同步** |
| `inferLoop` | `estimatePoses` → `ingestPose` | `setTimeout`，唯一會 `await` 的地方 |

面板的「畫面更新」與「推論更新」現在是獨立的兩個數字 ——
推論掉到 20/秒 時畫面應該仍維持在 60/秒。那就是解耦生效的證據。

**迴圈世代 token**：每次 `startLoops()` 遞增 `loopToken`，舊迴圈發現 token
對不上就自己退場。光檢查 `running` 不夠 —— 切換模型時舊的 `inferLoop`
可能正卡在 `await` 中間，resolve 時 `running` 已經被重設為 `true`，
它就會繼續跑成第二條推論迴圈。

## 遊戲流程

```
點「開啟相機」 → 看得到自己（ready）→ 手停在圓圈上 3 秒 → 開始 → 命用完 → 結束
```

**為什麼第一步一定要點擊**：相機還沒開就沒有手可以追，而且瀏覽器規定
相機權限與 AudioContext 解鎖都必須由真實點擊觸發。那一次點擊之後，
開始與重玩就都能用手勢了。

**懸停按鈕**（Kinect 式）：把手停在圓圈上，圈走完一輪就觸發。
`DWELL_MS = 2000`。手離開進度會倒退而不是歸零。
每走 1/6 圈滴一聲，讓人知道系統讀得到他。

**手在哪一定要看得見。** 選單狀態下會在掌刀位置畫一個脈動的 🖐 游標，
而且它必須畫在 `drawGameOver` / `drawReady` 的半透明遮罩**之後** ——
原本刀刃圓點是畫在遮罩之前，整個被蓋掉，使用者根本不知道手在哪、該往哪移。
完全偵測不到手時改顯示「舉起手，讓手肘也進到畫面裡」，
才不會讓人分不清是自己沒站好還是程式壞了。

**圓圈也可以用滑鼠點。** 體感是主要操作方式，但不該是唯一的 ——
追蹤失靈時要有逃生口。面板裡也有一顆「再玩一次」。

**生命值**：三條。漏接完整的水果扣一條，砍到炸彈也扣一條。
原版《水果忍者》砍到炸彈直接結束，但體感追蹤本來就會抖、誤砍機率比觸控高得多，
一刀斃命會讓人覺得是程式在找碴。最高分存在 `localStorage`
（無痕視窗會丟錯，所以讀寫都包了 try/catch，沒有紀錄也要能玩）。

## 寶物

| | 機率 | 效果 |
|---|---|---|
| 💎 寶石 | 6% | +5 分（雙倍期間 +10） |
| ⭐ 雙倍分數 | 4% | 7 秒內得分 ×2 |
| 🍌 慢動作 | 4% | 4.5 秒內水果變慢 |
| ❤️ 愛心 | 3% | 補一條命（命滿時不會出現） |
| 💣 炸彈 | 3%→20% | 扣 10 分、扣一條命 |
| 一般水果 | 其餘約 83% | +1 分，可切到八分之一 |

幾個刻意的設計：

- **寶物不會被切成兩半。** 它們是「拿到」不是「切開」，所以改成一圈光環加文字，
  玩家一眼就分得出剛剛發生的是什麼事。
- **漏掉寶物不扣命。** 那是獎勵不是義務。
- **命滿時不掉愛心**，不然會讓人覺得遊戲在浪費機會。
- **慢動作只放慢水果**，手的追蹤與刀痕維持原速 —— 兩個都放慢的話整個遊戲會變鈍。

## HUD

分數與生命值**都畫在 canvas 上**。之前分數是 HTML 覆蓋層、生命值是 canvas，
兩套畫法混用，結果分數又小又暗沒人注意到。現在分數有標籤、字夠大，
雙倍生效時會變成金色；生效中的寶物在右上角顯示剩餘秒數。

## 音效

全部用 Web Audio 合成，不帶任何音檔：

| | 做法 |
|---|---|
| 切中 | 帶通白噪音往下掃頻（「刷」）＋ 三角波（「咚」）。切得越細越輕越高 |
| 炸彈 | 低通白噪音長衰減 ＋ 鋸齒波下滑 |
| 扣命 | 短促下滑正弦 |
| 結束 | 四音下行 |
| 懸停 | 每 1/6 圈一聲方波，完成時兩聲上行 |

**自動播放政策**：在使用者手勢之外建立的 AudioContext 會是 suspended，
而且 Safari/iOS 上在手勢外呼叫 `resume()` 會被**無聲忽略**（不報錯，就是沒聲音）。
所以 AudioContext 只在真實 click 處理器裡建立（「開啟相機」和「示範切半特效」），
另外掛一次性 fallback，萬一第一次沒 resume 成功，之後任何點擊都能救回來。

## 韌性

| 狀況 | 處理 |
|---|---|
| 相機被拔掉 / 權限被撤銷 | 監聽 `MediaStreamTrack` 的 `ended` |
| **Safari 不發 `ended`** | 看門狗：`video.currentTime` 停止前進超過 2.5 秒就當斷線 |
| 分頁切到背景 | 暫停。否則 rAF 被節流，切回來那一瞬間 `dt` 暴衝，水果直接穿過畫面 |
| 人離開畫面 | 先不要丟水果，不然回來時命已經扣光 |

Safari 那條是查出來的已知問題（[WebKit bug 187896](https://bugs.webkit.org/show_bug.cgi?id=187896)）：
拔掉 USB 相機時不發 `ended`、`readyState` 甚至還回報 `live`。所以不能只靠事件。

## 面板數字怎麼讀

**效能**

- `畫面更新` ≥ 30 綠、< 20 紅。這是繪製迴圈，應該貼著螢幕更新率
- `推論更新` ≥ 20 綠、< 10 紅。**這一欄掉到個位數就是推論停了** ——
  畫面會照常動、其他數字照常更新，只有這一欄看得出來。先看它再看別的。這是模型迴圈。**它掉下去時畫面更新不該跟著掉** —— 跟著掉就表示解耦壞了
- `推論耗時 中位數` ≤ 15ms 綠、≥ 33ms 紅（33ms = 跟不上 30fps）
- `tensor 數量` 應該**固定不動**。持續上升就是 tfjs 的 WebGL tensor 洩漏
  （[tfjs#6937](https://github.com/tensorflow/tfjs/issues/6937)）

**追蹤品質**

- `刀刃抓到率` 低 → 站的位置、光線、或信心門檻太嚴
- `快揮時掉點率` 這是動態模糊的直接量測。上一幀正在快揮、這一幀抓不到就記一次。
  ≤ 5% 綠、≥ 20% 紅
- `左右手混淆丟幀` 兩隻手的刀刃點靠太近時會丟掉信心較低的那隻。數字一直爬
  表示雙手常被模型互換

**刀痕診斷**（切不到的時候先看這區）

- `刀痕成立率` 低 → 下面三個「擋掉」會指出是哪一道關卡的問題
- `擋掉：揮得不夠快` 只在「要揮動才算刀」開啟時才有意義
- `擋掉：幀間隔太久` 高表示 fps 太低，`MAX_LINK_MS`（260ms）不夠寬
- `擋掉：位移太大` 高表示追蹤在跳，`F.maxLink`（0.35 畫面寬）擋掉了
- `刀痕直線度` ≥ 0.975 才會拉直。長期偏低表示追蹤抖得厲害，
  或你習慣畫弧線而不是直劈
- `擋掉：沒揮出一刀` 高表示手在畫面裡但沒真的揮。切不到的時候先看這個
- `最長筆畫` 跟後面的門檻比。揮到最大還遠低於門檻，就把 `F.slashMin` 調低
- `最細切到` 1/2、1/4、1/8

`app.js` 開頭的 `F` 物件（距離門檻，單位是畫面寬的比例）、
`FOREARM_CM` / `PALM_CM` / `TIP_CM`（掌刀換算）、
